# Teem Builder v0 architecture

Status: normative target for the first useful version. [Vertical slice 1](vertical-slice-1.md) implements the completed subset through Awaiting review; [vertical slice 2](vertical-slice-2.md) implements independent review and bounded revision through Ready to merge; [vertical slice 3](vertical-slice-3.md) adds phone PWA dictation and Web Push. [Vertical slice 4](vertical-slice-4.md) proposes the current direction: a Telegram voice interface, a model-backed decider, real implementer and adversary agents, and GitHub pull requests. It supersedes slice 3's phone interface. This document adopts the authority and durability decisions in the [Astra review](review-astra-2026-09-23.md).

## Goal

Hands-off, voice-driven development. The user speaks a request from a phone. A decider turns it into bounded work. Implementer and adversary agents iterate until objective checks and an independent review pass. The user is contacted only when a decision, clarification, or finished pull request needs attention.

## Scope and topology

Assume one user, a few GitHub repositories granted ad hoc, and at most one active code-changing Run per repository. The server runs on TrueNAS as one process with one PostgreSQL database, which holds authoritative state, the queue, and the outbox. Durable artifact storage sits alongside it. One outbound-connected worker runs on a separate development machine. The server and worker reach Telegram, the model providers, and GitHub over outbound HTTPS only. Keep the server, worker, and versioned protocol in one repository. No separate scheduler, broker, or memory service is required.

| Role | Responsibility | Placement |
| --- | --- | --- |
| Decider | Interpret speech and text, ask clarifying questions, propose bounded work, report outcomes | Server module calling a hosted model; acts only through validated tools; output is untrusted input |
| Controller | Validate state transitions; authorize, schedule, retry, enforce budgets, reconcile, publish, and declare completion | Deterministic server code |
| Implementer | Change code within an authorized scope | Coding agent CLI in a worker container |
| Verifier | Run objective checks and adversarially review the exact candidate | Worker checks and an adversary agent from a different vendor in a fresh container |

Telegram is the user interface: voice notes and text in, text messages and decision buttons out. The server transcribes voice locally and echoes the transcript. Telegram's own notifications replace Web Push. The authenticated HTML pages remain for detailed evidence behind links.

## Authority and durable records

An observation or question does not start coding. The decider may create a **proposal**. A Run can be authorized only by a recorded user decision, made through a callback button bound to the specific pending action, or by a standing **project grant** that the user created the same way. Record the resulting decision and its source as an **Approval**. The controller validates authorization against current grants and state before dispatch. Execution results are **evidence**; they are neither authorization nor, alone, proof of completion. No model may grant permissions, extend budgets, or declare its own work complete.

| Record | Durable meaning |
| --- | --- |
| Project | GitHub repository and its grant state; a grant covers code/check/review/revise and publishing a `teem/*` branch and PR |
| Request | Submitted text, classification, conversation context reference, and deduplication identity |
| Run | One bounded objective with a versioned execution contract, budget, deadline, and completion condition |
| Task | One scheduled coding, check, review, or finalization step in a run |
| Attempt | One worker execution of a task, with assignment generation, lease, outcome, and usage |
| Candidate | Immutable code revision, base and head identity, preserved artifact, and linked evidence |
| Review | Immutable structured judgment, findings, uncertainty, and provenance from one review Attempt, bound to its exact Candidate, contract, context, and check evidence; evidence rather than authority |
| Approval | Recorded authorization decision granting or denying one action under a stated scope, source, target, and relevant state |

These are separate records with stable identities. Retry creates another Attempt; code revision creates another Candidate. A contract records objective, acceptance criteria, repository, base commit, context version, allowed actions, limits, and delivery condition. Material changes create a new contract version. Preserve explicit project decisions and their provenance separately from generated summaries. Current state and an append-only domain event are committed together; full event sourcing is unnecessary.

An Approval binds to the pending action and, where applicable, the candidate or artifact, the target, and the target state. A grant never implies merge, deployment, deletion, pushes to other branches, or access to another repository. Text and speech never resolve decisions; only authenticated callback buttons from the configured user do. Effective worker permissions are the intersection of server authorization and worker-local policy.

## Workflow and completion

1. Accept and deduplicate the Telegram update. The decider classifies it as an observation, question, proposal, or instruction, and may reply or ask for clarification. Persist a bounded proposal and execution contract before dispatch.
2. Resolve authorization from a project grant or an explicit decision. If none applies, keep the Run awaiting a scoped decision.
3. Queue a Task. The worker claims an Attempt, executes within an isolated container, and reports progress and results under a lease.
4. Freeze a committed Candidate and preserve its code artifact. Run objective checks; bind check results to the exact base/head commits, contract version, check configuration, and relevant environment.
5. Review that Candidate in a fresh session using the original requirements, candidate, relevant source, and check evidence. Do not give the reviewer the implementer's conversation or self-assessment. The reviewer has no authority to publish or alter the candidate.
6. If checks fail or a valid review requires changes, the controller queues a revision Task within the Run's limits; a successful revision preserves a new Candidate. Execution retries create Attempts of the same Task with the same inputs. New code or rebasing invalidates affected checks and review. Each new Candidate reruns all checks and receives an independent review. A blocked or uncertain judgment, or an exhausted limit, stops progress and asks the user. It never implies a pass.
7. At **Ready to merge**, the server publishes the exact preserved Candidate to a `teem/<run>` branch and opens a pull request, then checks in with the link. The user merges on GitHub. Deployment requires separate future workflows and authorization.

Start with one implementer (Claude Code), one adversary from a different vendor (Codex), and at most two revision rounds. The controller enforces a Run-wide Attempt cap, a revision cap, and an absolute deadline. The worker enforces subprocess timeouts and resource limits outside model prompts. Provider cost accounting, tool-call metering, and reservation/settlement are deferred.

Bind each accepted review to the preserved Candidate, contract version, check evidence/configuration, and the exact fresh review context and runner configuration. Retain older evidence as history; it cannot qualify a replacement Candidate. Reviewer output cannot change permissions, reset limits, or publish code. Count all Attempts, including failed or lost executions, and preserve the Run deadline across retries and revisions. A pass reaches Ready to merge only through a controller transaction validating current evidence and durable artifact integrity.

## Worker protocol and trust boundary

The versioned server/worker protocol must support enrollment and scoped credentials, capability reporting, task claim, lease renewal, progress, artifact upload, result submission, cancellation, and reconciliation after reconnect. Each assignment carries a stable Attempt identity and increasing generation. Protocol incompatibility fails cleanly. The protocol carries repository identities and authorized operations, never arbitrary host paths. The worker accepts only repositories under its locally allowed owners.

The server owns authoritative state. The worker keeps only a small durable journal of accepted attempts, execution identities, workspace locations, and unsent results for deduplication and recovery. Duplicate delivery must not launch a second process for the same Attempt. Stale generations cannot advance authoritative state, though their evidence may be retained. Lease expiry does not prove an old process stopped; the supervisor stops work when it cannot renew within the permitted window and reconciles uncertain outcomes before retrying.

Use isolated per-Attempt workspaces in rootless containers. A container's only writable mount is its workspace, and its only network path is an allowlisting egress proxy. Coding agents need network access to their model provider; this replaces the earlier no-network sandbox. A container receives only the model credential for its role. GitHub credentials and other privileged operations stay with the supervisor and server. Repository content and tool output cannot grant authority. Source goes only to the implementer's and adversary's providers. The decider receives conversation text, status, and summaries, but no source.

Persist candidates and evidence in durable artifact storage with database references and content hashes before reporting delivery. A commit present only on the worker does not qualify. Keep execution failures, worker connection loss, cancellation, and uncertain outcomes distinct. On server restart, resume from durable state. On worker reconnect, reconcile before replacing uncertain work. Never automatically repeat an external effect whose outcome cannot be determined; record and inspect such operations first. Branch push and PR creation are idempotent by Run identity.

## Deliberate exclusions and open questions

v0 excludes: Redis, NATS, microservices, a vector database, a generic workflow engine, multi-user tenancy, parallel coding, automated merge or deployment, ambient capture, group chats, and a native mobile app. Spoken replies, GPU transcription, and a live conversational voice mode come after the Telegram loop works.

The following choices remain open:

- Decider model and the provider fallback used when subscription usage limits are reached.
- Artifact retention policy.
- Worker credential rotation and GitHub App versus fine-grained tokens if more owners are added.
- Egress allowlist contents per project toolchain.
