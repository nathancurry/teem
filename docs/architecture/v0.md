# Teem Builder v0 architecture

Status: normative target for the first useful version. [Vertical slice 1](vertical-slice-1.md) implements a smaller subset. This document adopts the decisions in the [Astra review](review-astra-2026-09-23.md).

## Scope and topology

Assume one user, a few registered projects on trusted enrolled machines, and at most one active code-changing run per repository. Run one server process with one PostgreSQL database for authoritative state, queueing, and an outbox; use durable artifact storage; run one outbound-connected worker; serve a text PWA. Keep the server, worker, UI, and versioned protocol in one repository. No separate scheduler, broker, or memory service is required.

| Role | Responsibility | Placement |
| --- | --- | --- |
| Manager | Interpret user intent, assemble project context, propose bounded work, explain outcomes | Server module; model output is untrusted input |
| Controller | Validate state transitions; authorize, schedule, retry, enforce budgets, reconcile, and declare completion | Deterministic server code |
| Executor | Change code within an authorized scope | Worker supervised subprocess |
| Verifier | Run objective checks and independently review the exact candidate | Worker checks and fresh reviewer invocation |

The PWA submits text, shows status and evidence, presents specific decisions, and can request cancellation. The worker initiates HTTPS connections to claim work and report results; it has no inbound port. Foreground status may use polling or SSE. Notifications, if added, only prompt refresh of durable state.

## Authority and durable records

An observation or question does not start coding. The manager may create a **proposal**; an explicit user instruction, standing policy, or later user decision can authorize it only within a recorded scope. Record the resulting decision and its source as an **Approval**. The controller validates authorization against current policy and state before dispatch. Execution results are **evidence**, not authorization or proof of completion by themselves. No model may grant permissions, extend budgets, or declare its own work complete.

| Record | Durable meaning |
| --- | --- |
| Request | Submitted text, classification, conversation context reference, and deduplication identity |
| Run | One bounded objective with a versioned execution contract, budget, deadline, and completion condition |
| Task | One scheduled coding, check, review, or finalization step in a run |
| Attempt | One worker execution of a task, with assignment generation, lease, outcome, and usage |
| Candidate | Immutable code revision, base and head identity, preserved artifact, and linked evidence |
| Approval | Recorded authorization decision granting or denying one action under a stated scope, source, target, and relevant state |

These are separate records with stable identities. Retry creates another Attempt; code revision creates another Candidate. A contract records objective, acceptance criteria, repository, base commit, context version, allowed actions, limits, and delivery condition. Material changes create a new contract version. Preserve explicit project decisions and their provenance separately from generated summaries. Current state and an append-only domain event are committed together; full event sourcing is unnecessary.

Approval must bind to the pending action and, where applicable, candidate or artifact, target, and target state. A coding approval never implies merge, deployment, deletion, or access to another project. Use a deliberate authenticated decision for actions that need approval; ambiguous text cannot resolve multiple decisions. Effective worker permissions are the intersection of server authorization and worker-local policy.

## Workflow and completion

1. Authenticate and deduplicate the Request. Classify it as observation, question, proposal, or instruction. Persist a bounded proposal and execution contract before dispatch.
2. Resolve authorization for the proposed coding and checks. If none applies, keep the Run awaiting a scoped decision.
3. Queue a Task. The worker claims an Attempt, executes within an isolated workspace, and reports progress and results under a lease.
4. Freeze a committed Candidate and preserve its code artifact. Run objective checks; bind check results to the exact base/head commits, contract version, check configuration, and relevant environment.
5. Review that Candidate in a fresh session using the original requirements, candidate, relevant source, and check evidence. Do not give the reviewer the coder's conversation or self-assessment for its initial judgment. The reviewer has no authority to publish or alter the candidate.
6. If revision is required, create new attempts and candidates within the Run's limits. New code or rebasing invalidates affected checks and review. Stop for a user decision when limits or uncertainty prevent progress.
7. Complete only after a reviewed, committed Candidate and its evidence are durably preserved and visible as **Ready to merge**. Merge and deployment require separate future workflows and authorization.

Start with one coder, one reviewer, and at most two revision rounds. The controller enforces run-wide limits on time, tool use, attempts, revisions, and estimated cost, including manager and reviewer calls. Deadlines and subprocess resource limits are enforced outside model prompts.

## Worker protocol and trust boundary

The versioned server/worker protocol must support enrollment and scoped credentials, capability reporting, task claim, lease renewal, progress, artifact upload, result submission, cancellation, and reconciliation after reconnect. Each assignment carries a stable Attempt identity and increasing generation. Protocol incompatibility fails cleanly. The protocol carries project IDs and authorized operations, never arbitrary host paths; the worker maps IDs to locally configured repositories.

The server owns authoritative state. The worker keeps only a small durable journal of accepted attempts, execution identities, workspace locations, and unsent results for deduplication and recovery. Duplicate delivery must not launch a second process for the same Attempt. Stale generations cannot advance authoritative state, though their evidence may be retained. Lease expiry does not prove an old process stopped; the supervisor stops work when it cannot renew within the permitted window and reconciles uncertain outcomes before retrying.

Use a dedicated worker-owned clone and isolated workspaces. Git worktrees are workspace isolation, not a security boundary. The supervisor keeps its credentials and privileged operations outside agent subprocesses. OS controls constrain filesystem, network, credentials, and resources for coding **and** repository checks. Repository content and tool output cannot grant authority. Project data policy applies before sending source, transcripts, summaries, or logs to a provider.

Persist candidates and evidence in durable artifact storage with database references and content hashes before reporting delivery. A commit present only on the worker does not qualify. Keep execution failures, worker connection loss, cancellation, and uncertain outcomes distinct. On server restart, resume from durable state. On worker reconnect, reconcile before replacing uncertain work. Never automatically repeat an external effect whose outcome cannot be determined; record and inspect such operations first.

## Deliberate exclusions and open questions

No Redis, NATS, microservices, vector database, generic workflow engine, multi-user tenancy, parallel coding, automated merge or deployment, continuous voice, or ambient capture in v0. Voice, notifications, additional workers, and provider diversity can be considered after the text workflow is reliable.

The following choices remain unresolved; implementations must satisfy the boundaries above without assuming an answer here:

- Exact artifact backend and retention policy, including whether Git bundles are the initial candidate format.
- Single-user authentication method, worker enrollment mechanism, and credential rotation.
- Worker OS isolation mechanism and project data routing policy for model providers.
- Initial coding/reviewer adapters and how objective checks are configured per project.
- Concrete timeout, retry, cost, and resource limits; the controller must enforce them once chosen.
